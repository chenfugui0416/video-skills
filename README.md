# video-skills

> 一人自媒体的 AI Agent 全链路内容系统：从一条灵感到四个平台发布完成的状态回填，内容生产全自动，人只做一次终审。本文是这套系统的完整设计与实测报告。

**通道验证状态**：X 自动直发 ✅ · 微信公众号 HTML 交付 ✅ · 微信视频号手动通道 ✅ · 小红书交付包 ✅ · 抖音 ⏳ 待连接

---

## 1. 这是什么

一个「一人 + AI Agent」的自媒体运营系统。运营者只负责三件事：给灵感、终审、手动上传必须手动的平台；其余——选题整理、四平台稿件生成、配图、视频产线、部分平台的自动发布、状态回填、数据复盘——全部由 AI Agent 按照本仓库的方法执行。

系统要解决的核心矛盾是：**内容生产可以全自动化，但平台风控决定了发布必须「一平台一策略」**。哪些平台能自动直发、哪些必须交付给人工、状态在多平台之间如何不散架，是这套系统的真正价值所在。

## 2. 系统全景

```
灵感 ──▶ 发布包 ──▶ 原文.md（唯一事实源）
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
    四平台稿件        视觉素材          视频产线
  小红书/公众号/X/抖音   imgs/       TTS→渲染→混音
        │               │                │
        └────────▶ 统一确认单（用户终审）◀┘
                        │ 用户确认后
        ┌───────────┬───┴────────┬───────────┐
        ▼           ▼            ▼           ▼
   X 自动直发   公众号 HTML    视频号手动   小红书手动
        └───────────┴─────┬──────┴───────────┘
                           ▼
             发布状态.json / 发布总表.md 回填
                           ▼
                  四平台完成 → 归档 → 数据复盘
```

每条内容一个发布包（目录即数据单元）：

```text
内容库/待发布/YYYY-MM-DD-标题/
├── 原文.md            # 事实、数字、链接、结论的唯一来源
├── 小红书.md          # 平台适配稿（重组结构语气，不改事实）
├── 微信公众号.html    # 排版完成的交付物
├── X.md               # 主帖 + 串文
├── 抖音.md            # 图文卡片文案（复用 X 稿）
├── 配图方案.md / 配图提示词/ / imgs/
├── video/成片.mp4     # 视频产线产物（按需）
├── 统一确认单.md       # 终审入口
└── 发布状态.json       # 状态枢纽
```

## 3. 核心设计原则

1. **一条灵感，一份事实源。** `原文.md` 是唯一事实来源；平台稿可以重组结构、语气、长度和标题，但不得改变事实或制造未经验证的数据与结论。这消灭了多平台内容互相漂移的经典问题。
2. **生成与发布之间有一道人闸。** `approvalStatus` 字段只有用户能改；任何脚本不得代写。立即发布是向外不可逆动作，调用方必须显式声明（`--now` / `immediate=True`），漏传排期参数报错而不是静默发布——防止代码路径漏参导致误发。
3. **状态增量回写。** 所有环节对 `发布状态.json` 只增不改；`已发布` 状态只在平台返回成功后写入。脚本回写永远不覆盖人的判断。
4. **自动化止步于风控边界。** 宁可给用户一个 30 秒的手动上传流程，不冒账号被限流封禁的风险（详见 §5.4 的工程决策案例）。

## 4. 平台通道矩阵

| 平台 | 发布方式 | 技术通道 | 决策依据 |
|---|---|---|---|
| X | **全自动直发** | 主 Chrome + JXA 驱动 intent 页 | 2026-08 实测成功，见 §5.1 |
| 微信公众号 | **HTML 源码交付** | 行内 CSS 单文件，用户插件导入 | 排版自动化收益极高；发布接口不稳定，导入是最稳一环 |
| 微信视频号 | **手动上传** | 成片 + 发布要素清单 | 自动通道实测不可行，见 §5.4 |
| 小红书（图文） | **手动交付包** | `图片/` + `文案/` 双目录 | 平台检测脚本自动发布 |
| 小红书（视频） | **手动上传** | 同视频号 | 同类处理 |
| 抖音 | 自动（待登录） | CDP 驱动已登录浏览器 | 登录后启用 |

风控自律（全平台通用）：单账号单平台每天 1–2 条、不并发、失败不自动重试。

## 5. 关键技术实现

### 5.1 X 自动直发：JXA + intent 页五步法

不用第三方 API（会被风控误判拦截），不复制 Cookie，不建隔离浏览器实例——**直接驱动用户本人正在运行、已登录的主 Chrome**，全程不碰用户的标签页：

```bash
osascript -l JavaScript -e '
const app = Application("Google Chrome");
const win = app.windows()[<含 x.com 的窗口>];   // 先扫描定位，不硬编码
const restore = win.activeTabIndex();
const url = "https://x.com/intent/post?text=" + encodeURIComponent("全文");
win.tabs.push(app.Tab({url}));            // 新开 intent 标签，URL 一步带入全文
const myIdx = win.activeTabIndex();       // 记住自己的标签（1-based）
win.activeTabIndex = restore;             // 立即切回用户视图
'
```

完整流程五步：开 intent 标签 → 短暂激活等表单渲染 → 验证文本填充 → 点 `[data-testid=tweetButton]` → toast 确认后从时间线提取帖子 ID 做详情页二次验证，最后只关闭自己开的标签。

实测踩坑记录（每条都真实撞过）：

| 坑 | 症状 | 解法 |
|---|---|---|
| 后台标签被 Chrome 节流 | compose 对话框存在但内部空壳（HTML 长度 ≈1200、无输入框） | 短暂激活标签等表单初始化 |
| 发帖按钮混淆 | `tweetButtonInline`（常驻侧栏、禁用）长得像发帖按钮 | 只点 `[data-testid=tweetButton]` |
| 并行操作干扰 | 用户/其他 Agent 切走活动标签甚至关掉你开的标签 | 每次操作前按 URL 重新定位，不缓存 index |
| 成功误判 | 对话框关闭 ≠ 发布成功 | 以平台 toast「Your post was sent」+ 详情页正文验证为准 |

已验证不可行通道：第三方 CLI 写入（被平台风控拦截，读取正常但发帖一律拒绝）；复制 Cookie + 隔离实例（技术可行但违反「只用主浏览器」安全原则，弃用）。

### 5.2 视频产线：阶梯式花钱闸

手绘动画科普视频产线（720×960 竖屏、35–45 秒、AI 配音），按「先免费后花钱」组织成命令阶梯：

```bash
node release-flow.mjs "包名" plan         # 盘点 + 建议下一步（免费）
node release-flow.mjs "包名" prompt       # 出分镜提示词 → 模型产出分镜
node release-flow.mjs "包名" tts          # 配音 + 逐字时间轴（免费）
node release-flow.mjs "包名" dryrun       # 渲染工程演练（免费）
node release-flow.mjs "包名" render --yes # 真渲染（花钱！必须显式确认）
node release-flow.mjs "包名" mux          # 混音 + 白片校验
```

设计要点：免费步骤全部通过才允许进花钱步骤；渲染崩溃有兜底回写（底层异常退出来不及写状态时由驱动脚本补记 `失败待处理`）；成片入库走幂等对账脚本（默认 dry-run，核对后 `--apply`），只增不改。

### 5.3 微信公众号 HTML 交付规范

交付物固定为单文件 `微信公众号.html`：UTF-8 完整文档、行内 CSS（不依赖外部样式和脚本）、图片相对路径 + `alt`、引用带查询日期、本地双击可预览且手机宽度无横向滚动。时效信息（价格、政策、工具能力）写稿当天复核。插件需要单文件导入时再额外生成 Base64 嵌入版。

### 5.4 工程决策案例：为什么视频号是手动上传

这是一个「知道何时放弃自动化」的案例。视频号创作平台是 wujie 微前端架构——表单挂在 `document.querySelector("wujie-app").shadowRoot` 里，且加载时机不稳定；更致命的是 macOS 系统文件面板（NSOpenPanel）在该页面上反复被推到屏幕外坐标，键事件注入被系统以 `bounds_mismatch` 拒绝。

**结论：自动化的边界由投入产出比和账号风险决定，不由技术洁癖决定。** 最终交付形态是一个 30 秒手动流程：成片 + 标题 + 简介 + 话题 + 两个必选项（AI 生成内容标识必勾、位置选不显示）。人做 30 秒，比修一个每次都可能坏的系统便宜得多。

## 6. 状态机与数据契约

六个状态词贯穿全链路：`草稿` → `待生成` / `待连接` → `待确认` → `已发布` / `失败待处理`。

`发布状态.json` 最小契约：

```json
{
  "strategyContext": {"contentPillar": "", "funnelStage": "", "audienceSegment": "", "primaryCta": ""},
  "sourcePlatform": "idea|xiaohongshu|wechatOfficialAccount|x|douyin",
  "approvalStatus": "待确认",
  "assetsStatus": "待生成",
  "video": {
    "status": "待确认",
    "finalPath": "video/成片.mp4",
    "platforms": {"wechatChannels": {"status": "已发布", "url": "", "publishedAt": ""}}
  },
  "platforms": {"x": {"status": "已发布", "url": "", "publishedAt": "", "notes": ""}},
  "performance": {}
}
```

回写责任：脚本只做增量；`approvalStatus` 仅用户可改；`已发布` 仅在平台返回成功后写入；手动平台等用户告知后回填；四平台全部完成才归档到 `内容库/已发布/`。

## 7. 安全与合规红线

- **浏览器驱动死规矩**：绝不杀用户正在运行的 Chrome（任何进程、无论状态）；只驱动用户已登录的主浏览器；不复制 Cookie、不建隔离实例、不另起进程。端口冲突只做只读排查并报告。
- **凭据永不落盘**：API Key、Cookie、Token 只存系统 Keychain 或 600 权限 env 文件；一切规则、文章、日志、发布记录里只记配置位置，不记值。
- **AI 内容标识合规**：AI 生成内容发布必须勾选平台标识选项（境内《人工智能生成合成内容标识办法》2025-09-01 施行，未标识会被取消推荐资格）；标识本身不影响正常流量分发。
- **发布意图显式化**：立即发布必须显式声明；漏参报错而非静默发布；单账号单平台限频。

## 9. 如何使用

本仓库同时是一个 Agent Skill——`SKILL.md` 是主流程指令，`reference.md` 是深度技术参考。把它放进你的 Agent 技能目录（或按你的 Agent 规范加载），对 Agent 说：

> 「同步发行这个发布包」/「出视频」/「发 X」

Agent 会按 §2 的链路执行，在统一确认单处停下来等你终审。

```text
video-skills/
├── README.md      # 本文（系统设计与实测报告）
├── SKILL.md       # Agent 主流程指令（死规矩 + 通道表 + 各平台方法）
└── reference.md   # 深度参考（JXA 代码、坑位清单、状态 schema、生图模板）
```
